# 视频制作质量：工作汇报预设

Status: proposed（设计稿，未实现）。2026-11-27 用户确认了 Decision Ledger 里标"用户"的分支，其余由我按现有代码定，开放项见文末。对应 OpenSpec change：`ocu-video-report-kit`。代码几乎全在 OCU 仓库，WebUI 仓库只放本计划、change 和 OCU pin。

## 背景

科普讲解工具箱（`docs/plans/2026-11-16-ocu-video-explainer-kit.md`，change 已归档为 `2026-11-26-ocu-video-explainer-kit`）已经上线：模型只写 `script.json`，画面由审过的场景组件渲染。课程、宣传、汇报三类仍走 `free-form.md`，由模型从零写动画代码。用户选定先做汇报。

现有汇报成片（27 上 `runs/baseline/report-sales-q3/r1-a1` 和 `runs/after/report-sales-q3/r1-a1`，都走 free-form）版式尚可，问题主要在**数字是否可信**。请求只给了五个数，即销售额 1260 万元、同比 +18%、新签 42 家（华东占一半）、回款率 93%（比上季度 +5 个百分点）、Q4 目标 1500 万元。画面上却还有：

- 模型自己推算的数：「去年同期 1068万」（1260/1.18）、「上季度回款率 88%」、「华东 21 家」；
- 请求里根本没有的说法：「重点客户板块表现突出」「华东市场继续成为公司最重要的增长引擎」「现金流状况持续向好」。

前三个算对了，但它们是模型心算出来的，没有任何机制能保证算对；后几句则是编造的。汇报给领导看，一个错数就足以让整条视频作废，所以这一刀的首要目标是数字准确，其次才是好看。

## 设计

### 1. 同一个工具箱，按 `preset` 分支

- `script.json` 顶层新增可选键 `preset`。没有这个键，就是今天的科普脚本，校验、渲染逐字节不变（must-preserve，要有测试钉住）。值为 `"report"` 时，用下面的汇报骨架和汇报场景集合。
- 不另开工具箱，也不复制文件：schema、渲染器、`kit.mjs`、timeline、配音、背景音乐、check 和 render 的作业机制都共用，按 preset 选骨架、场景集合和主题。
- `version` 仍是 1。科普脚本不受影响，所以不升版本号。

### 2. 汇报的 `script.json`

- 骨架：封面 → 2–5 节（节名不超过 6 字，每节 1–4 个场景）→ 小结 → 片尾。小结用来写要点和下一步。
- 总时长 60–180 秒，和科普一样由配音决定。
- 顶层新增 `data`，存放所有数字，场景和旁白只能引用它，不能直接写数字。见第 3 节。
- 场景候选：
  - 新做的：`cover`（标题、部门、期间）、`kpi-grid`（2–4 个指标，可带增减）、`target-progress`（实际与目标，附完成率）、`share`（部分占整体，用环形图或堆叠条）、`trend`（多期柱图或折线，突出最新一期）、`ranking`（横向条形，排前 N 名）、`table`（不超过 5 行 4 列）。
  - 沿用科普的：`key-number`、`chart`、`comparison`、`concept-card`、`process-steps`、`timeline`、`image-callouts`、`summary`、`end-card`。凡是带数字的字段，在汇报里都改成引用 `data`。汇报不允许 `custom` 场景：模型自写的 TSX 可以绕过所有数字规则。
  - 最终只保留用户在样片集里批准的。
- 配图：允许用生图配图，流程和科普相同（`kit image`）。

### 3. 数字：只来自数据，派生数由代码算

**数据项**（`data` 里的条目）有三种来源，每项都有 `id`、`label` 和 `unit`：

- **用户文字**：写 `value` 和 `quote`，`quote` 是用户原话里含这个数的片段。check 要求 `value` 的写法（规范化后）确实出现在 `quote` 里。
- **上传的表格**：先用 `kit data "<路径>"` 导入，再写 `from: {table, row, column}`。值由代码从文件里读出，模型不经手。
- **派生**：写 `derive: {op, of: [id…]}`。`op` 只能取 `sum`、`diff`、`product`、`ratio`、`growth`、`pp-diff` 六种，由 kit 计算：
  - `ratio` 和 `growth` 的结果单位是 %；
  - `pp-diff` 的单位是"个百分点"；
  - `sum` 和 `diff` 要求各项单位相同；
  - `product` 用于"42 家里占一半"这类计算，得 21 家。"一半"是 quote 规则唯一接受的文字写法，对应 50%。
- **百分数**：一律按百分数本身记，`93` 就是 93%。`sum`、`diff` 不能用于百分数，百分数之差用 `pp-diff`。

**显示规则**：

- 用户给的数按原样显示：数字照用户的写法，单位照 `unit`，不换算万/亿，不加千分位。
- 派生的百分数保留到一位小数，整数时不带小数。
- 每个派生数在 `kit check` 的输出里列出它的公式和来源。

**旁白**：

- 旁白里的数字一律写成占位符 `{<id>}`，由 kit 展开成显示文本再送去配音。
- 旁白和画面文字里出现占位符以外的阿拉伯数字，check 拒绝。例外有两种：期间写法（`2026年`、`9月`、`Q3`、`第3季度` 等），以及从导入表格原样显示的表头和行名。
- 字幕块的 16 字上限，以及配音文件名里的哈希，都按展开后的文本计算。

**表格导入**：

- `kit data` 接受 `/mnt/user-data/files/` 里的 `.csv`、`.xlsx`。xlsx 默认读第一个工作表，可用 `--sheet` 指定。
- 第一行必须是表头。上限 50 行、12 列。数值单元格由 python 读出，并按单元格的数字格式生成显示文本（百分比格式记为百分数）。公式单元格取其缓存值。合并单元格和不支持的数字格式一律拒绝，并指出位置。表格文件计入 check 的哈希，重新导入后必须重跑 check。
- 结果写进 `data/<name>.json`，并打印列名和前几行，供模型引用。
- 不合规的文件直接拒绝，并说明是哪一行、哪一列。

**图表**：

- 柱图的纵轴从 0 开始，不允许截断。
- `share` 各部分之和不得超过整体。
- `trend` 和 `ranking` 只能引用同一张表的一列，或同单位的一组数据项。

**做不到的事，要写明**：

- kit 只能看到 `script.json`，看不到用户的那条消息，所以它证明的只是"内部一致"：每个数都能追到某个数据项，每个派生数都算对了，每条文字来源的数都出现在它的 `quote` 里。
- 这个 `quote` 是不是用户的原话、模型有没有在旁白里编造原因，kit 都查不出来。这两件事交给第 3a 节的规则和评测阶段的核对（第 6 节）。

### 3a. 文字：根据稿子来，不清楚就问用户

- 用户给的消息和附件就是"稿子"。旁白和画面上的每一句话都要能在稿子里找到依据：数字按第 3 节处理；原因、业务板块、评价、计划等定性内容，只能复述或概括稿子里写了的。
- 稿子没写清楚、但视频需要的内容，在写 `script.json` 之前一次性问用户，等用户回答再做，不得自己补。需要问的包括：期间或部门不明、数字口径或单位有歧义、表格里不知道该用哪一列、用户要求讲原因而稿子里没写原因等。
- 稿子已经够用时不问，直接做。开场和结尾的口号（如"乘胜追击"）不算事实陈述，可以写。
- `report-kit.md` 把这一步写成工作流的第 0 步：先列出视频需要的信息，逐项对照稿子，缺了就问。

### 4. 主题、音乐、配音

- 汇报主题做亮色和深色两版。亮色在用户已选的 `light` 基础上调强调色；深色参考现有汇报成片里观感不错的深蓝底。两版都放进样片集，由用户挑一套。
- 背景音乐沿用现有曲库，推荐 `upbeat/corporate` 一类。配音沿用 `generate_speech` 和现有流程。

### 5. check

在科普已有的机械检查之外，汇报新增：

- 数据项的结构，以及 `quote` 规则；
- 派生数：公式合法，没有除以零，单位能对上；
- 旁白和画面里没有裸写的数字；
- 图表纵轴从 0 开始，占比之和不超过整体；
- 每个表格引用都指向 `data/` 里实际存在的单元格。

拼图之后的是/否清单，增加汇报专用的几问：画面上每个数都带单位吗？对比的两项是否同口径？每句话是否都能在稿子里找到依据？

### 6. 评测与验收

- **数字来源清单**：已在 27 上核实，评测保存的 transcript 不含工具调用参数，取不到模型写的 `script.json`。所以汇报出片时，kit 在成片旁边另外发布 `<name>.figures.json`，列出每个数、它的来源和展开后的旁白。driver 把它和 MP4 一起收集；用户也可以用它核对每个数是怎么来的。
- **请求集**：
  - 现有的 `report-sales-q3` 只把 `repetitions` 从 1 改为 2，其他字段不变。
  - 新增 4 条汇报请求，草稿由我起，用户确认后才固定：2 条只有文字，2 条带附件，附件是一个 csv 和一个 xlsx，放在 `deploy/eval/fixtures/`。
  - 每条跑 2 遍，共 10 对。
  - 每条请求都写到"稿子够用"，不需要追问。评测的 driver 不会回答问题，所以模型如果在这几条请求上追问了用户，这一遍按没有出片计。另加 1 条故意缺信息的 `smoke` 请求（例如只说"把三季度汇报做成视频"），用来验证模型会追问而不是编造；这条不参加盲评。
- **driver**：支持请求里的 `attachments`，先经 WebUI 文件 API 上传，再挂到消息上，与生产链路一致。
- **phase**：新增 `report-before` 和 `report-after` 两个 phase，结果写进 `runs/report-before/`、`runs/report-after/`，不碰已有的 `runs/baseline` 和 `runs/after`。`requests.json` 里的非汇报条目保持原样。
- **顺序**：先用 27 上当前的部署跑 `report-before`，再做任何工具箱改动。和科普时一样，渲染成功率阈值在这一轮之后定，check 通过率阈值事先定，两者都在 after 轮之前经用户确认，写进 change。
- **验收（三条全满足才翻路由）**：
  1. 10 对成片打乱顺序给用户两两盲评，新版至少赢 8 对；
  2. 稿子核对：10 条新版成片里，画面和旁白中出现的每个数字，都等于请求里的数或附件里的值，或者是由它们经第 3 节公式算出的数，错误数为 0；每句定性说法都能在稿子里找到依据，人工复核，编造数为 0。数字部分由脚本读 kit 随成片发布的数字来源清单（`<name>.figures.json`，列出每个数及其来源，以及展开后的旁白）做比对，再抽帧人工复核。中文数字写的数量（一半、两成）也算数字，人工复核。开头和结尾的口号不算编造。旧版成片也做一遍核对，只作对照；
  3. 渲染成功率和 check 通过率达到阈值。

### 7. skill

- 新增 `skills/public/remotion/report-kit.md`，参照 `explainer-kit.md` 写汇报的骨架、数据项、占位符、`kit data` 和场景表。
- `SKILL.md` 的路由加一条"工作汇报（汇报）→ 工具箱"。和科普一样，这一刀**只在验收通过后合并**。在此之前合并的工具箱代码没有入口，不影响生产。

4. 数字显示规则（汇报专用，科普仍用 `formatCount`）和汇报主题的亮、深两版。

## Not In Scope

- 课程、宣传两种预设。
- 竖屏 9:16、3D、音效库。
- 上传 logo 或自定义品牌色。用户选的是"允许生图配图"，没有选品牌定制。
- 一次导入多张工作表；数据透视；读取 Excel 里的图表对象。
- 改动 `generate_speech`、生图链路、视频开关和 skill 门控。
- 新增 npm 依赖。
- 改变科普脚本的格式或成片。
