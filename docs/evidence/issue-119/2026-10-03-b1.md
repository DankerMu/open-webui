### 3. Official requirements and acceptance-machine headroom

The [Community Docker requirements](https://helpcenter.onlyoffice.com/docs/installation/docs-community-sys-reqs-docker.aspx), retrieved during this campaign, state CPU ≥ single-core 2 GHz (dual-core recommended for production), RAM ≥ 4 GB, free disk ≥ 40 GB and swap ≥ 4 GB, dependent on host OS. The same page's workload table gives a single-core 2.8 GHz CPU for fewer than 100 concurrent active users.

The [Docker repository README](https://github.com/ONLYOFFICE/Docker-DocumentServer#recommended-system-requirements) instead labels its figures *recommended*: dual-core 2 GHz, RAM ≥ 4 GB, swap ≥ 2 GB and free disk ≥ 2 GB. Its retrieved blob is `1760dc6168f51ecd3169621c753759907ab6df30`. These are distinct published figures, not interchangeable citations.

Acceptance-machine headroom: **not measured — this campaign has no LAN access**. The plan's below-minimum acceptance profile is not a fresh measurement. It remains an acceptance environment, not a capacity proof; an operator must record its actual shortfall against the cited figures. Local Docker reports 14 CPUs and 16,747,859,968 bytes total memory; the isolated server was limited to 4 CPUs / 6 GiB. A post-probe sample with 21 editors open showed DocumentServer at 788.7 MiB / 6 GiB. This is one observation, not a peak or load benchmark.

### 5. Connection boundary and broker usage query

Twenty-one distinct document keys and distinct synthetic users simultaneously reached `onDocumentReady` in edit mode. Document 21 accepted `B1-CONCURRENT-21`; its status-6 export contains that marker. No page/console errors or editor `onError` events occurred, including a 10-second observation after that edit. The authenticated `license` response returned `connections = connections_view = 2147483647`, with empty `quota.users` and `quota.users_view` despite the 21 live editors.

The documented command API has no global live-connection-count query: [`license`](https://api.onlyoffice.com/docs/docs-api/additional-api/command-service/license/) exposes licence/server/user-quota information; [`info`](https://api.onlyoffice.com/docs/docs-api/additional-api/command-service/info/) requests status and users for one document key, not a global connection count. The empty quota arrays must not be interpreted as zero active editors.

The [9.4.0 changelog](https://github.com/ONLYOFFICE/DocumentServer/blob/v9.4.0/CHANGELOG.md) says “Removed the limitation of 20 simultaneously opened documents”; the release README comparison table still says “up to 20 maximum”. The measured 21-document admission agrees with the changelog. It does **not** establish unlimited capacity, legal entitlement or behavior at larger counts. A broker must not invent a 20-connection refusal from this run.

Evidence: `concurrent-21.json`, `concurrent-export-proof.json`, `command-docs.json`.

### 6. Last close to status-2 callback

Qualified DOCX run: after observing document-state `true → false`, close the last browser page without requesting force-save. The status-2 callback arrived **5.337–5.358 seconds** after the close boundary, bracketed by helper-side monotonic events immediately before and after `page.close()`. Its downloaded DOCX contains `B1-POLICY-DOCX`, SHA-256 `bdde8ae9e00883ca7a4e02497b95029484d2eea10b55cb86d565b59e83436d7c`.

Evidence: `b1-policy-docx.json`, `policy-export-proofs.json`, `state-before-cleanup.json`. This is one measured latency interval, not a timeout guarantee. The earlier `close-proof.json` probe did not confirm that its final keystroke became a document-state change; its absent final marker is retained but is not used as content-preservation or data-loss evidence.

### 7. Callback download origins

### 8. Connection-cap event

**No cap event observed at 21 distinct simultaneous documents.** All 21 reached edit mode; there is no measured 20-cap event code to give a host-page implementation. This is a concrete absence at the tested boundary, not an assertion that no larger boundary exists.

The measured `onError` code `-18` belongs to shutdown-mode connection loss, not a connection-cap refusal. It must not be reused as a cap code. The operator approved removing the unobserved cap-specific consumer paths; ordinary editor/API failures remain errors.

### 10. Shutdown preparation and restart reset

Shipped command: `/usr/bin/documentserver-prepare4shutdown.sh`, SHA-256 `5dead241b747a219cd3cd3f067d06e155716d4e22a59e15401cc5cc3ccea7f08b`. Two live editors, XLSX and PPTX, had new server-acknowledged edits and no requested force-save. The command exited 0 after **30.250 seconds**. Both documents produced status-2 downloads containing their `B1-XLSX-SHUTDOWN` / `B1-PPTX-SHUTDOWN` markers; both browser hosts reported connection-loss warning `-18`.

A fresh DOCX opened before restart reported `onError -18` and did not become ready during 20 seconds. `docker restart --time 60` on the same isolated container completed; a new DOCX then reached edit mode, accepted input and returned force-save command `error: 0`, with no browser errors. Thus shutdown saved and disconnected **both documents open in this test**, and restart cleared the admission-blocking mode. This is not a proof over arbitrary document counts or types.

Evidence: `shutdown-precondition.json`, `shutdown-command-result.json`, `shutdown-proof.json`, `b1-before-restart.json`, `b1-after-restart.json`, exported files.

### 11. Editing without the WebUI cookie

The browser carried a synthetic WebUI cookie; the actual HTTP/WebSocket proxy stripped `Cookie` before forwarding to DocumentServer. The retained snapshot contains **1,678 requests with an incoming cookie and zero with a forwarded cookie**. Real three-format edits, exports and 21-document admission succeeded through that proxy. Only presence booleans were logged; no real WebUI session credential was used.

Evidence: `state-before-cleanup.json`, measurement source `host.py`, positive browser records.

### 12. Force-save `userdata`

The signed command sent `userdata = b1-userdata-ba756a35215f1674`; the authenticated status-6 callback returned the exact value, with `forcesavetype: 0`. The expected nonce matched and a deliberately different nonce did not. An unsigned callback control returned HTTP 401. The downloaded DOCX contained the input marker.

Evidence: `docx-export-proof.json`, callback/event records. These qualify the measurement oracle; they are not tests of the future production broker.

### 13. Editor-native save with user force-save disabled

With `editorConfig.customization.forcesave = false`, real DOCX input followed by the native save shortcut produced document-state `true → false` and **no callback during 199.701 seconds**. A later explicit command produced the measured status-6 callback, so the callback receiver was live. The observation is bounded and DOCX-specific; it does not claim that no callback can ever occur. Native save is not the broker's future persist/publish operation.

Evidence: `native-save.json`, DOCX event records and `docx-export-proof.json`.

### 14. Minimal tested iframe capabilities

The minimal tested outer iframe is `sandbox="allow-scripts allow-same-origin"`, with an **empty `allow` attribute**. DOCX, XLSX and PPTX opened, accepted input and yielded status-2 exports containing the markers under that policy. `allow-forms` was unnecessary for these flows.

Removing `allow-same-origin` caused opaque-origin CORS failures and a service-worker `SecurityError`; removing `allow-scripts` blocked host script execution. Neither control reached document-ready within 20 seconds. These are capability-removal controls, not unexpected positive-run errors.

The Docs API's own inner iframe has no `sandbox` attribute and requests `allow="autoplay; camera; microphone; display-capture; clipboard-write;"`. The empty outer feature list sufficed for the measured open/edit/export flows; clipboard, camera, microphone, screen capture, printing and popup/download UI were not certified. The measurement host is synthetic and same-origin with its outer page; it does not prove the security of a future WebUI/OCU embedding topology.

Evidence: `b1-policy-*.json`, `policy-export-proofs.json`, actual exported OOXML.

## Design-assumption disposition

| Assumption | Observation within this campaign |
| --- | --- |
| `forcesave` echoes `userdata` | Matches: exact nonce in authenticated status-6 callback |
| Shipped shutdown preparation saves and closes open documents | Matches for both dirty documents held open during the command |
| Restart clears shutdown-preparation mode | Matches: fresh admission fails before restart and edit succeeds after |
| Native editor save does not itself produce a callback | Matches the bounded 199.701-second DOCX observation with user force-save off |
| Editor works without the WebUI cookie | Matches the measured formats and concurrent sessions; zero forwarded cookies |

The five assumptions have supporting observations with the limits above. The operator accepted the measured absence of a cap event at 21 documents as the concrete detection result and approved removing the unobserved cap contract. The selection decision does not extrapolate beyond 21 documents or certify the acceptance machine.

## Isolation and cleanup

DocumentServer had only a fresh internal Docker network. The disposable helper also had an edge network for loopback-only ports; no existing service, Docker socket or business directory was mounted. Direct external-IP egress from DocumentServer failed with curl exit 7. The helper's synthetic source/callback service and proxy were reachable through the intended paths.

The browser was stopped, both owned containers were removed with `docker rm -f -v`, and the two named networks were removed. Inspection identified all eight anonymous volumes as mounts of the owned containers before removal. Before/after identity sets match exactly: **24 images, 16 pre-existing containers, 15 volumes and 12 networks**. No image, pre-existing resource or unrelated cache was deleted. Evidence: `isolation.json`, `cleanup-ownership.json`, `cleanup-result.json`.
