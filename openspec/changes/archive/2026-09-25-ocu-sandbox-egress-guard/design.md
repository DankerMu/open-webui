# Sandbox egress guard design

## Context

User policy decision: #25 comment5831571393; DNS prerequisite: #79. The topology uses IPv4 bridge networks; the orchestrator connects to sandbox CDP/ttyd through gateway-bound published ports. Replies therefore travel from the sandbox toward the control subnet. Docker's DOCKER-USER path is FORWARD-only and post-DNAT; host-local destinations require INPUT protection.

## Goals and non-goals

Governing invariant: sandbox-initiated traffic passes this policy only to explicit allowed IPv4 destinations, never control-plane or metadata; control-initiated replies remain possible, and unknown/unsupported address families are not an escape path.
Must preserve: existing foreign firewall rules, normal control-plane traffic, configured external access, non-destructive network/container handling, and `up.sh` owned-process cleanup.
Non-goals: Docker/DNS lifecycle implementation (#79), full env provisioning (#26), runtime overlay smoke (#27), domain or protocol/content allowlists, automatic firewall-backend conversion, reboot daemons, real privileged/Docker execution before #36.

## Decisions

1. Configuration: `OCU_SANDBOX_EGRESS_ALLOW` must be present; whitespace-trimmed comma-separated IPv4 addresses or canonical CIDRs, with empty whole value meaning no new egress. Reject malformed/non-IPv4 entries and empty interior entries; canonicalize/deduplicate without broadening networks. A broad range never overrides control-plane/metadata denies. No default public-internet grant. This is destination-address policy, not domain filtering or data-loss prevention; other host rules may still deny an allowed destination.
2. Resolve the protected bridge from authoritative Docker network inspection using `OCU_SANDBOX_NETWORK`, the network ID and its explicit bridge-name option or Docker's `br-<first12id>` convention. Validate the existing non-internal bridge/IPAM contract and usable interface name; bind hooks by ingress interface so source-IP spoofing cannot evade them. Inspect rather than guess a host Docker TCP address: the deployment uses a Unix socket. Read required bridge-netfilter sysctls and fail on unsupported packet paths instead of claiming enforcement.
3. One owned IPv4 filter chain is reached first from DOCKER-USER and INPUT for this bridge. Its ordered rules are: conntrack `ESTABLISHED,RELATED` in `REPLY` direction returns; control subnet DROP; metadata `169.254.169.254/32` DROP; one RETURN per allowlisted destination; unconditional DROP. Returning preserves downstream host policy instead of globally accepting packets. ORIGINAL-direction established flows remain subject to the current allowlist, so tightening policy does not preserve an unauthorized sandbox-originated connection. Require Docker's unconditional DOCKER-USER hook to precede terminating FORWARD rules; missing or bypassed Docker hooks fail preflight.
4. IPv6 is not an allowed destination family for this IPv4 deployment. Use a small owned IPv6 DROP chain, reached first for sandbox ingress in INPUT and FORWARD, to prevent link-local or accidental IPv6 activation bypasses. Do not assume a single IPv4 IPAM entry proves IPv6 cannot carry packets. Require the IPv6 firewall/bridge-filter prerequisites; unsupported hosts fail with a named reason. No IPv6 allowlist or silent fallback.
5. Installation owns only its reserved chains and jump rules. Serialize cooperating installer/checker processes with an owned private lock. Populate only owned chains through `iptables-restore --noflush` / IPv6 equivalent, with bounded xtables waits; never flush or create DOCKER-USER, INPUT or FORWARD. Keep a working top jump while removing stale/duplicate owned jumps; repair misordering by inserting the guarded top hook before removing old owned hooks. Preserve unrelated rules and policies. A failed operation aborts deployment; do not claim a cross-family transaction or undo unrelated host state.
6. Checker is read-only apart from lock ownership. Inspect actual chains, normalized ordered rules, unique first hooks and bridge identity; reject missing, duplicate, stale, misplaced or unexpected owned-policy rules with a rule/chain-specific diagnostic. Share one production policy definition with the installer, not two independently maintained rule inventories. Fake expected policy and packet judgments must not import that production definition.
7. `deploy/up.sh` explicitly distinguishes an unset allowlist from an empty deny-all value. After successful network provisioning, run installer and checker unconditionally through `run_owned`, before the first Compose start; a reused bridge does not skip them. Failures and handled interruption retain the established no-start/private-snapshot-cleanup guarantees. Do not change the initializer or unrelated lifecycle code.

The reserved policy namespace serves one sandbox bridge on a host. If existing managed hooks belong to a different bridge, refuse implicit migration rather than removing protection from that interface; operators must resolve old sandbox/network state deliberately. Changes to allowlist contents on the same bridge remain reconcilable.

## Evidence boundaries

- Fake iptables state exercises the actual installer/checker CLI: install twice -> one ordered copy; seeded foreign rules survive; old allowlist/duplicate/misordered owned state reconciles; missing Docker chain, absent backend/sysctl, invalid address and restore failure -> nonzero with no service start. Independent process locking covers concurrent cooperating invocations.
- An independent tiny packet-policy evaluator consumes the installed fake rule state, not production helpers. Cases: listed IPv4 permitted by this policy; unlisted public/company/host destinations dropped; control/metadata remain dropped under a broad allow; control-originated CDP/ttyd replies return; sandbox-originated established packets to unlisted destinations drop; forged source IP on sandbox ingress still drops; non-sandbox traffic unchanged; IPv6 denied. This evaluates policy semantics, not kernel/NAT behavior.
- Qualify judges with isolated faults: missing final DROP, reversed hard-deny/allow ordering, missing reply exception, missing INPUT/IPv6 hook, source-subnet-only hook, duplicate or bypassed jump, and ignored installer/check failure. Restoration must return to green for the intended reason.
- Final #36 evidence must run the real scripts twice, inspect iptables/ip6tables state, exercise both forwarded and local-host paths plus CDP/ttyd replies, and prove DNS is covered after #79. No privileged commands or Docker CLI are executed locally or newly enabled in CI now.

## Risks and migration

The backend is Linux Docker with the iptables interface (including its nft frontend), not Docker's native nftables backend or rootless networking. A missing DOCKER-USER chain is an error, not permission to create an inert placeholder. Host firewall reset/reboot invalidates readiness and requires deployment reconciliation; no continuous enforcement agent is added. Kernel/iptables-nft atomicity and packet traversal remain explicitly unverified until #36. Configuration changes may stop existing sandbox egress immediately; they never delete containers or networks.

The DNS host-namespace path remains open until mandatory #79 supplies explicit allowed upstreams and rejects incompatible existing sandboxes. Installation of this guard alone is not full all-egress readiness. Review focus: hook reachability/order, reply direction, independent state evidence, foreign-rule preservation, and honest DNS/kernel limitations.
